# 排班规则修改校验逻辑改造 Spec

| 项目 | 内容 |
|---|---|
| 文档类型 | 功能改造设计 Spec |
| 涉及端 | 门店医院Web端（store-web）、排班微服务（careld-schedule-service） |
| 涉及页面 | http://localhost:5175/schedule-rule（排班设置） |
| 状态 | 已开发（2026-09-12，API 端到端验证通过） |

---

## 1. 背景与问题

### 1.1 现状

`ScheduleRuleServiceImpl.updateRule`（careld-schedule-service）对编辑排班规则实行**一刀切限制**：

```java
// 区间内已有预约时限制修改
if (slotMapper.countBookedInRange(storeId, startDate, endDate) > 0) {
    throw new BusinessException(4002, "该规则区间内已存在预约，不可修改，请先处理相关预约");
}
```

只要规则区间内存在**任意一条预约**，整个规则即锁定，任何字段均不可修改。

### 1.2 问题

现实运营场景中，旺季人员激增时门店需要随时调整排班：

- **增加每小时接待上限**（"加床位"）
- **新增接待时段**
- **延长已有时段的结束时间**

以上均为**纯扩容操作**，不影响任何已有预约，却被 4002 错误一并拒绝。门店只能先逐一取消区间内全部预约才能改规则，运营成本极高，逻辑明显不合理。

---

## 2. 目标

将"有预约即禁改"的一刀切，改为**按修改影响面校验**：

1. 扩容类修改（不影响已有预约）→ 直接允许
2. 缩减类修改 → 仅当实际影响已预约时段时才拒绝，且报出具体冲突时段
3. 删除规则沿用现有校验（有预约不可删），不在本次改造范围

---

## 3. 修改类型分类

| 类型 | 具体操作 | 对已有预约的影响 |
|---|---|---|
| **扩容类** | 提高某时段 capacity；新增时段；延长时段结束时间；扩大日期区间 | 无影响 |
| **缩减类** | 降低 capacity；删除时段；缩短时段；新增/扩大例外日；缩小日期区间 | 可能影响 |
| **中性修改** | 仅修改例外日备注文本；区间内无预约时的任意修改 | 无影响 |

判定方式：不逐字段 diff，而是基于"**新规则物化结果与已预约 slot 的兼容性**"统一校验（见 4.2）。

---

## 4. 详细规则

### 4.1 编辑流程（updateRule）

1. 规则存在性校验（404）——**保持不变**
2. storeId 补齐、validateRule 基础校验（日期区间、时段起止/整小时/同类不重叠/capacity>0）——**保持不变**
3. 与其他规则的日期区间重叠校验（排除自身，4001）——**保持不变**
4. **删除原 4002 一刀切校验**，替换为 4.2 的影响面校验
5. 更新主表、重建时段（4.3）——调整实现

### 4.2 影响面校验（新）

设区间内**已预约 slot**（booked_count > 0）集合为 B，按新规则逐条检查：

| 场景 | 校验规则 | 报错 |
|---|---|---|
| B 中 slot 的日期时间，在新规则物化结果中**仍存在** | 新容量必须 ≥ 该 slot 已约人数 | `时段 HH:mm~HH:mm（YYYY-MM-DD）已预约 N 人，新上限 M 人小于已约人数，无法修改` |
| B 中 slot 在新规则物化结果中**不存在**（时段被删/缩短/该日变例外日） | 直接拒绝 | `时段 HH:mm~HH:mm（YYYY-MM-DD）已存在预约，新规则不再覆盖该时段，无法修改` |

- 若 B 为空（区间内无预约），跳过本节所有校验，任意修改放行
- 错误码：沿用 4002，message 替换为上述具体描述

### 4.3 时段重建策略

当前实现：`deleteUnbookedInRange` 删除区间内全部未约 slot，再 `materializeSlots` 全量生成。

问题：保留的已预约 slot 与新物化生成的 slot 在相同日期+起止时间会发生唯一键冲突（schedule_slot 存在 store+date+start 唯一约束——实现时以实际索引为准）。

新策略：

1. 区间内**已预约 slot 保留不动**（booked_count > 0）
2. 区间内未约 slot 全部删除（沿用 deleteUnbookedInRange）
3. 物化新规则时，**跳过与已预约 slot 同日期同起止时间的 slot**，其余照常生成
4. 未约 slot 的 max_capacity 一律按新规则生成

```
事务内执行：校验(4.2) → updateById 主表 → 删除原 periods/exceptions → 写入新 periods/exceptions
          → deleteUnbookedInRange → materializeSlots（skip 已约 slot）
```

### 4.4 删除规则（deleteRule）

维持现状：区间内有预约（4003）拒绝删除，无预约可删。本次不改。

## 5. 接口与错误码

| 接口 | 变化 |
|---|---|
| `PUT /api/v1/schedule-rules/{id}` | 移除"有预约即 4002"，改为按 4.2 校验；成功响应不变 |
| `POST /api/v1/schedule-rules` | 不变（新建本就有 4001 重叠校验，无预约概念） |
| `DELETE /api/v1/schedule-rules/{id}` | 不变 |

错误码汇总：

| code | 场景 |
|---|---|
| 4001 | 日期区间与其他规则重叠 |
| 4002 | 修改影响已预约时段（message 指明具体时段与原因） |
| 4003 | 删除时区间内有预约 |

---

## 7. 验收标准

1. 区间内有预约时，编辑规则**仅提高容量** → 保存成功，未约 slot 按新容量生效，已约 slot 不变
2. 区间内有预约时，编辑规则**新增一个时段** → 保存成功，新时段正常生成可约
3. 区间内有预约时，编辑规则**降低某已约时段容量至低于已约人数** → 4002，message 含具体时段
4. 区间内有预约时，编辑规则**删除/缩短已约时段**或**将已约日期设为例外日** → 4002，message 含具体时段
5. 区间内无预约时，任意修改（含缩减、例外日）→ 全部放行
6. 扩容后新生成 slot 与已约 slot 无重复/无唯一键冲突
7. 删除规则行为不变（有预约拒删）
8. 物化生成 slot 的 booked_count、状态与预约数据无漂移（重建后预约仍指向原 slot）

---

## 8. 边界场景

| 场景 | 预期 |
|---|---|
| 延长时段跨过已有已约 slot（如原 8-9 点已约，延长为 8-10 点） | 8-9 点保留已约数据，9-10 点新生成，视为扩容放行 |
| 例外日新增在已有预约的日期 | 该日已约 slot 不再被新规则覆盖 → 4002 拒绝 |
| 日期区间起点/终点缩短，裁掉的天无预约 | 放行；裁掉的天有预约 → 4002 |
| 编辑时仅改例外日备注 | 放行（无 slot 影响） |
| 区间内 slot 状态为停用（status≠1）但未约 | 视为未约 slot，重建时被删除重生成 |

---

## 9. 实现要点备忘

- 核心文件：`backend/careld-schedule-service/.../service/impl/ScheduleRuleServiceImpl.java`（updateRule / materializeSlots）
- `countBookedInRange` 需返回 slot 明细（或新增查询），仅计数不足以支持 4.2 逐条校验
- `materializeSlots` 需支持 skip 集合参数（或先在内存算出已约 slot 的 date+startTime 集合）
- 全程保持 `@Transactional` 原子性
