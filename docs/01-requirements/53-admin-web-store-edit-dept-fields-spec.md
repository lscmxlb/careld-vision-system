## 1. 需求清单

| # | 子项 | 说明 |
|---|---|---|
| 99-1 | 服务电话 | 新增到「加盟时间」上一行 |
| 99-2 | 科室类型 | 新增到「加盟时间」下一行 |
| 99-3 | 收费标准 | 新增到「床位数量」下一行（单位元/次） |
| 99-4 | 机构性质 | 原行移动到「医院编码」上一行（即表单首行） |

调整后行序：机构性质 → 医院编码 → 所属运营中心 → 所属代理商 → 医院名称 → 所在地区 → 详细地址 → **服务电话** → 加盟时间 → **科室类型** → 床位数量 → **收费标准** → 联系人 → 联系电话。

---

## 2. 现状诊断

- 该三项数据存于 `store_department`（医院端基础信息维护的即该门店第一条科室记录，见 spec 52），门店表 `store_info` 无对应列（`center_id` 亦为派生字段，不落库）。
- admin-web 已有 `departmentApi`（`/departments` 增删改查）与科室管理页，医院编辑弹窗可直接复用。
- 编辑弹窗原有校验要求「所属运营中心」必填：无运营中心归属的门店（如 STORE001）本就无法提交——既有约束，本次不改。

## 3. 改造设计

`frontend/admin-web/src/views/store/list.vue` + `types/index.ts`：

| 项 | 设计 |
|---|---|
| 表单行序 | 机构性质移至首行；服务电话/科室类型/收费标准按需求插入对应位置 |
| 数据分离 | 科室三项使用独立 `deptDialogForm { id, deptType, servicePhone, chargeStandard }`，不混入 `formData`（避免把科室字段提交给 `PUT /stores/{id}`） |
| 编辑回显 | `handleEdit` 调用 `departmentApi.getDepartmentList({ storeId, page:1, size:20 })` 取第一条（与医院端基础信息同源），回填三项 |
| 保存 | 门店保存成功后，若 `deptDialogForm.id` 存在则 `PUT /departments/{id}`（`servicePhone` 空串→null、`chargeStandard` 空→null，支持清空） |
| 无科室门店 | 三项禁用并提示「该医院暂未创建科室，请先在医院端基础信息中维护」（科室名称不在本弹窗采集，无法静默建科室） |
| 新增模式 | 三项 `v-if="isEdit"` 隐藏（门店尚未创建科室，且新增流程本就由店长登录医院端后维护） |
| 类型定义 | `Department` 增加 `servicePhone`/`chargeStandard`，`deptType` 注释改为 5 类 |

## 5. 遗留与说明

1. 一个门店存在多个科室时，编辑页仅展示/维护第一条（与医院端基础信息口径一致）；科室级完整管理仍用 admin-web「科室管理」页。
2. admin 端不能在此弹窗为「尚无科室」的门店创建科室（缺少科室名称输入）；如需支持可另提。
3. STORE001 无运营中心归属，编辑时被「所属运营中心」必填校验拦住、无法提交——既有约束，非本次引入。
4. 0×0 隐藏视口下弹窗关闭过渡不播放，`destroy-on-close` 不触发销毁，输入框内部分内部态在连续同页开关中可能残留显示；真实浏览器（正常过渡）不受影响，验证时以组件状态为准。
5. 与 #63–#104 同属未提交改动，等待确认后一并入库。
